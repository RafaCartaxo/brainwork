## Como ler a tabela

- **Baseline reutilizável:** dado/estado que a população inicial do seed já carrega.
- **Ação de teste (cria em tempo de execução):** mutation/payload chamado por um CT especificamente para validar o cenário — não é algo que o baseline deixa pronto de antemão.
- **Consulta (não prepara estado):** função que só lê dados já existentes.
- **Dependência observada (não confirmado que o seed prepare):** aparece em comentário/shape de código/texto de UI, sem teste real que a exercite.
- Estados de conhecimento: **Confirmado** (visto direto no TR, no código ou numa captura real de API/execução), **Inferido**, **A confirmar**.

## Contexto de produto (Conhecimento > Módulos > Assinaturas, 09/10/2026) — separado do que o código confirma

> Esta seção é contexto de produto (fonte: Notion, importado em 2026-07-17), não requisito literal do TR nem evidência de código/teste. Não resolve nem substitui as linhas "A confirmar" da tabela acima.

- **Classificação do produto** (própria, não é a mesma redação do TR): "Eletrônica simples" (eventos na timeline que identificam autor/cargo/setor — **sem** menção a certificado); "Digital SoGov" (certificados emitidos pela própria Lacuna, **não** vinculados a autoridades ICP-Brasil, mas com validade como assinatura digital); "Digital ICP-Brasil" (certificados de autoridades vinculadas à ICP-Brasil, via mesma API Lacuna).
- **A documentação de produto descreve o campo da tela** ("Tipo de assinatura", citado repetidamente no texto importado do Notion) **como oferecendo** só 2 opções: "SoGov (default) ou ICP" — **não 3**. Isso **não foi observação direta da UI nesta fatia** (não abri a tela do produto) — é o que o texto da doc afirma. Mesmo assim, é uma informação relevante: **segundo essa mesma doc**, a classificação conceitual de 3 tipos e o campo descrito como selecionável na tela (2 valores) não são a mesma lista — diferente também da taxonomia de 3 alíneas do TR (1.40.2.1.a/b/c).
- **Não presumo** que `type: 'SOGOV'` do código corresponda formalmente a "Eletrônica simples" do TR (1.40.2.1.a) nem a "Digital SoGov" da classificação de produto — a doc de produto descreve "Digital SoGov" como uma assinatura **com certificado** (ainda que não ICP-Brasil). O que o código de fato confirma, por canal: **via UI (e2e)**, senha comprovada (`fillSignaturePassword`, 14 arquivos), sem nenhuma seleção/validação de certificado visível; **via API**, só o envio do valor `'SOGOV'`/`'DEFAULT'` como payload — o mecanismo de autenticação por trás desse valor no canal de API **não está confirmado** por nenhum teste lido. Essa tensão entre o que a doc descreve (certificado) e o que a UI exercita (senha) **não foi resolvida nesta fatia** — registro só a existência dela, sem inferir qual lado está certo ou se o certificado acontece de forma transparente por trás da senha.

## O que falta para este recorte virar preset executável (resumo)

- **Assinatura eletrônica avançada/qualificada (certificado ICP-Brasil)** — nenhuma cobertura de código/teste encontrada; os 14 arquivos de teste e2e que exercitam o canal UI usam só senha, e o canal API só confirma o valor `'SOGOV'` enviado (sem confirmar o mecanismo de autenticação por trás dele).
- **Campo `type`/`signatureType` nunca confirmado por leitura** — só enviado como payload; nenhum teste lê de volta o campo e confirma seu valor persistido.
- **Tensão entre documentação de produto e código**: a doc descreve "Digital SoGov" como assinatura com certificado (não-ICP-Brasil); o canal UI exercita só senha, sem seleção de certificado visível, e o canal API só confirma o valor `'SOGOV'` enviado, sem confirmar o mecanismo por trás dele — não resolvida nesta fatia.
- **Modal "Assinaturas digitais" (seleção de tipo)** — confirmado que existe (citado para testar sua ausência num fluxo específico), mas nunca aberto/exercitado com conteúdo ou seleção real.
- **`type: 'SOGOV'` aparece de forma condicional no baseline, não garantida** — o payload de criação de 2 dos 3 workflows do baseline (`workflow`, `workflowAttachment`) configura esse valor na Etapa 02, mas `getWorkflowOrCreate` reaproveita um workflow pré-existente sem reconciliar o payload — a garantia só vale quando o workflow é criado do zero nesta rodada de provisionamento. Fora desse mecanismo de workflow, o valor `'SOGOV'` é só o que `createSignatures`/`executeSignatures` enviam em tempo de teste.
