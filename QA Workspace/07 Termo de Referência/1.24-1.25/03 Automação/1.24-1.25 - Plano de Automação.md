# 1.24-1.25 — Plano de Automação

> [!info] Sobre esta nota
> Plano técnico para automatizar os 38 casos de teste dos itens 1.24/1.25 no repositório `sogov-automation-test` (Cypress). Escrito antes de qualquer mudança no repo — mexer no repo é passo separado, autorizado depois. Ver [[1.24-1.25 - Casos organizados para Qase|casos organizados para Qase]], [[1.24-1.25: Execução|planilha de execução]] e [[1.24-1.25 - Casos de Teste|casos em Dado-Quando-Então]].

## Resumo

Os itens **1.24** (tipos de acesso: servidor, cidadão PF, cidadão PJ) e **1.25** (validação de credenciais, bloqueio por tentativas, ciclo de vida da identidade — Ativo/Licença/Férias/Inativo/Suspenso) já viraram 38 casos de teste (CT-001 a CT-038, 5 suítes) documentados nesta mesma pasta. Este plano define **como** automatizá-los no repo `sogov-automation-test` de forma organizada e reaproveitável — sem duplicar o que já existe, sem inventar mutation/seletor sem confirmar, e sem virar 38 tarefas artesanais desconectadas.

Investigação feita lendo o código real do repo (não presumido):
- Já existe uma base de auth (`auth.api.commands.js`, `auth.e2e.commands.js`) cobrindo só login bem-sucedido — nada de senha errada, bloqueio ou status.
- Já existe um padrão de subagentes prontos pra escrever teste (`.claude/agents/criar-teste-{e2e,api}.md` + skills `.claude/skills/criar-teste-{e2e,api}/`), com convenções obrigatórias de reuso: nunca duplicar command, login sempre via `cy.session`, setup idempotente `getXOrCreate`, docs só recebem acréscimo.
- `updatePublicAgent` (mutation) e `publicAgentByInstance` (query) já retornam `workStatus`/`statusStart`/`statusEnd` — ponto de partida real pra popular status de identidade, mas **não confirmado** que a mutation aceita esses campos.
- Não há acesso a banco de dados via Cypress task nem menção a bloqueio/tentativas em todo o repo (grep vazio) — é território genuinamente novo.
- `cypress/support/test-data/fixed-accounts.js` está marcado no próprio arquivo como obsoleto ("substituído... pode deletar") — **não** reaproveitar como ponto de partida para CPFs fixos de cenário.
- O agente principal do setup global (`AGENT_CPF`) é cacheado via `cy.session` e reusado por *todos* os 127 testes já existentes — bloqueá-lo ou mudar seu status quebraria a suíte inteira. Cenários de bloqueio/status precisam de agentes de teste isolados e dedicados.

## Pontos-chave

### 1. Organização de pastas/arquivos no repo (proposta)

Novo domínio `auth`, espelhando o padrão `<domínio>/<entidade>.<layer>.cy.js` já usado por `processing/`, `public-agent/` etc:

```
cypress/testes/api/entities/auth/
  login.api.cy.js               (Suíte 1 — CT-001 a CT-009)
  credentials.api.cy.js         (Suíte 2 — CT-010 a CT-012)
  lockout.api.cy.js             (Suíte 3 — CT-013 a CT-019)
  identity-lifecycle.api.cy.js  (Suíte 4 — CT-020 a CT-036)
  audit-sessions.api.cy.js      (Suíte 5 — CT-037, CT-038)

cypress/testes/e2e/entities/auth/
  login.e2e.cy.js
  credentials.e2e.cy.js
  lockout.e2e.cy.js
  identity-lifecycle.e2e.cy.js
```

Um spec por suíte (não por CT), um `describe` por suíte, um `it` por CT nomeado com o ID (`CT-013 — ...`) para rastreabilidade Qase → código.

Commands e factories a **estender** (nunca criar arquivo paralelo pro que já existe):
- `cypress/support/commands/api/auth.api.commands.js`
- `cypress/support/commands/e2e/auth.e2e.commands.js`
- `cypress/support/test-data/factories/user.factory.js`

Docs a estender (só acréscimo de seção, nunca reescrita):
- `docs/commands/api/auth.api.md`, `docs/commands/e2e/auth.e2e.md`
- Novo arquivo `docs/business-rules/api/auth-identity-lifecycle.md` (mesmo estilo de `document-lifecycle.md`) pra registrar as regras de bloqueio/quarentena/status assim que confirmadas — os subagentes já encontram isso automaticamente da próxima vez.

### 2. Estratégia de reaproveitamento (commands/factories)

- `cy.loginAgentExpectFailure` / `cy.loginCitizenExpectFailure` — paralelos a `loginAgent`/`loginCitizen`, mas **sem** `cy.session` (login com senha errada não deve ser cacheado nem quebrar o contrato de sucesso do command original).
- `cy.attemptFailedLogins(loginFn, args, times)` — implementa o shared step SS-03 (N tentativas) uma única vez, reaproveitado por vários CTs.
- `cy.editPublicAgentStatus(...)` — wrapper fino sobre `cy.editPublicAgent` já existente, só depois de confirmar (seção 4) que a mutation aceita `workStatus`/`statusStart`/`statusEnd`.
- `cy.fillLoginIdentifierCitizen` / `cy.loginCitizenUI` — cobre o campo único CPF/CNPJ da tela do cidadão, ainda sem command E2E.
- Nova factory `makePublicAgentStatusInput` em `user.factory.js`, com os valores reais do enum de `workStatus` (não adivinhar a partir de `makeFinishAgentExternalRegistryInput`).
- **Usuários de teste isolados por cenário** (bloqueio, Licença, Férias, Inativo, Suspenso) via `getPublicAgentOrCreate` com nome fixo por cenário — nunca reusar o agente global do setup. Não reaproveitar `fixed-accounts.js`; seguir o padrão de e-mail derivado de CPF/CNPJ já usado em `e2e.js`.

### 3. Camada API vs E2E — regra geral

API cobre a regra de negócio (o que o backend decide); E2E só o que só existe na tela (mensagem visível, botão desabilitado/oculto, aviso de quarentena). Evita duplicar a mesma asserção nas duas camadas.

| Suíte | Camada primária | Racional |
|---|---|---|
| 1. Tipos de acesso | API; E2E só onde a tela do cidadão é o próprio gap | Aceitar/rejeitar CPF/CNPJ e contexto de sessão é checável 100% pela resposta da API |
| 2. Credenciais | API; E2E só para validação client-side (campo obrigatório) | Mensagens de erro genéricas são check de status/body |
| 3. Bloqueio | API para os 7 casos; no máx. 1 E2E "smoke" pro aviso na tela | Contagem/threshold é mais rápido e estável via API que repetir form 5x |
| 4. Ciclo de vida | Mista — login permitido/negado e bloqueio de escrita → API; aviso na tela → E2E | Aplicação em tempo real (CT-025/033) fica por último, depende do mecanismo confirmado |
| 5. Transversais | Mista — auditoria via API se houver endpoint; sessões simultâneas via 2 chamadas de API concorrentes | Mais determinístico que 2 browsers reais |

### 4. Caminho de investigação técnica (pré-requisito antes de codar Suíte 3 e 4)

Não presumir shape de mutation/enum. Ordem:
1. Reler `edit.agent.api.cy.js` como referência.
2. Introspection do tipo `UpdatePublicAgentInput` ou captura real (DevTools/HAR) da tela de admin alterando status.
3. Confirmar se existe mutation dedicada de status separada de `updatePublicAgent`.
4. Confirmar valores literais do enum `workStatus` (incluindo o nome real de "Suspenso").
5. Só então estender a factory.
6. Repetir o processo para a mutation de desbloqueio (Suíte 3) quando for a vez dela.

Isso é investigação técnica, fora do mandato dos subagentes de teste (eles não inventam mutation sem request/response real) — deve virar sessão dedicada, e o resultado alimenta os briefings da seção 6.

### 5. Faseamento

- **Fase 0** (pré-requisito, fora do código): os 38 CTs precisam estar validados manualmente em HML antes de automatizar aquela suíte — fluxo já estabelecido (`SKILL_INICIAR_AUTOMACAO`, `FLUXOS.md`).
- **Fase 1** — investigação técnica (seção 4), curta e única, não gera teste ainda.
- **Fase 2** — infraestrutura reaproveitável (commands, factory, agentes de teste isolados). É o que mais entrega organização e reaproveitamento: depois dela, os 38 CTs viram combinações dos commands prontos.
- **Fase 3** — escrita dos 38 casos em lotes por suíte, da menos para a mais dependente de gap: **Suíte 1 → Suíte 2 → Suíte 5 → Suíte 3 → Suíte 4** (deixando CT-025/033 por último dentro da Suíte 4).

### 6. Geração dos 38 briefings em lote

Em vez de 38 idas-e-vindas pelo fluxo conversacional das skills (`criar-teste-e2e`/`criar-teste-api` SKILL.md, que perguntam 1 caso por vez), montar os briefings **em lote, agrupados por Shared Step** (SS-01 a SS-06 do Qase — o próprio Termo já mapeia "usado em: CT-X, CT-Y..."), e disparar direto para os subagentes executores (`criar-teste-e2e.md`/`criar-teste-api.md`), pulando a etapa de perguntas — o Termo já contém as 4 respostas que a skill pediria (persona, elementos/roteiro, dado, critério de sucesso).

Reduz de 38 disparos para ~10-15 lotes, preservando 1 `it()` por CT no código final. O único campo que o Termo não fornece (request/response real) vem da Fase 1, uma vez por família de operação — não por CT. Extração feita por leitura direta do Qase (não por script de parsing), pois há nuances (casos redundantes válidos, notas de revisão) que exigem leitura humana/LLM.
