# 1.24-1.25 — Sincronização com a Qase

> [!info] Sobre esta nota
> Registra o que foi feito na rodada de sincronização de 31/08 entre o vault (fonte única, ver [[1.24-1.25 - Casos de Teste]]) e o projeto `SGV` na Qase, e aponta pra ferramenta reutilizável — pra não precisar reconstruir esse processo do zero num próximo Termo de Referência.

## O que foi feito

Os 39 casos do projeto `SGV` na Qase estavam desatualizados/incompletos em relação ao vault (23 vazios, 1 corrompido, 2 com informação já desmentida). Sincronizado via API REST (não CSV — import por CSV duplica em vez de atualizar):

- **25 casos atualizados** — conteúdo completo (precondição/pós-condição/passos), correção do card corrompido (`id 5`), correção da regra de acesso de leitura em Licença/Férias, e correção dos nomes de nível de permissão no CT-020.
- **2 casos excluídos** — órfãos já absorvidos por outros 4 casos desde 19/08 (comparação de mensagens de erro entre cenários).
- **1 caso novo criado** — equivalente ao CT-017 (desbloqueio manual pelo servidor), que nunca tinha existido na Qase.
- `priority` foi deixado de fora de propósito (fica pra preencher manualmente na Qase) — e `behavior` nunca é enviado (mapeamento de valor incerto).

## Ferramenta reutilizável

Script e dados vivem no repositório de automação, não no vault:
`sogov-automation-test/scripts/qase-sync-1.24-1.25/`
- `corrections.json` — o que muda em cada caso (formato legível).
- `sync.js` — aplica via API, com dry-run por padrão, `--inspect=<id>` (leitura segura) e `--only=<id>` (teste isolado antes do lote).
- `README.md` — documenta tudo, inclusive os achados sobre o comportamento da API da Qase.

## Achados técnicos (valem pra qualquer sincronização futura com a Qase)

- Import via CSV não faz merge — duplica casos existentes em vez de atualizar.
- A API faz update parcial de verdade — campo não enviado não é tocado.
- Campos como `severity`/`type`/`automation`/`status` são **números** na API real, mesmo que o export mostre texto — sempre confirmar contra um `GET` real (`--inspect`) antes de escrever.
- Exclusão via API (`DELETE`) é definitiva, sem lixeira documentada — tratar como irreversível.
- A Qase tem shared steps nativos (`GET /v1/shared_step/{code}`) — vale conferir se já existem antes de escrever conteúdo novo, mesmo que a decisão final seja não usá-los.

## Processo recomendado pra replicar

1. Exportar o estado atual da Qase e cruzar caso a caso com o vault (por conteúdo, não só por ID/título).
2. Escolher uma fonte única no vault e absorver nela o que só existe nas outras versões.
3. Montar o `corrections.json` só com o que realmente muda por caso.
4. `--inspect` num caso real pra confirmar o formato exato dos campos antes de escrever.
5. `--only=<id>` num caso de baixo risco antes do lote inteiro.
6. Só então aplicar o lote completo, e conferir por amostragem.
